## D6: college CSVs contain literal-NaN sensor dropouts, not just FEMTO (2026-07-21, found while smoke-testing M1-T1 against real files)
`college.py`'s first version raised `ValueError` on any NaN in a chunk, treating it as malformed data (command.md: "never silently coerce malformed data"). Running the adapter against the real first file crashed - the source CSV genuinely contains rows with literal `NaN` text in the temperature columns (82 rows) and, separately, in the vibration columns (40 rows), from real sensor read failures, not corruption.
Resolution: NaN is not malformed here - it's the source's own explicit missing-value marker, matching the same principle already applied to FEMTO temperature (`command.md` section 3.2 / `data-contract.md`: "Missing temperature remains missing and receives an availability flag. Do not fabricate or globally forward-fill"). `read_college_chunks` now passes NaN through unchanged instead of raising, and still raises on genuine structural malformation (wrong column count / unparseable non-numeric non-NaN text). See `docs/dataset-audit.md` for full counts. `docs/data-contract.md`'s `temp_available` field is file-level and now known to be too coarse for college data (gaps are row/window-level, and can hit vibration too) - flagged as a follow-up for M2, not changed in this pass.

## D10: college's naive RUL baseline is trivially perfect (MAE=0.0) by construction, not a real result (2026-07-21, found running M4 after fixing D9)
After fixing D9, the college walk-forward's naive baseline scored exactly `mae_seconds=0.0`, `rmse_seconds=0.0` on every fold. This is not a bug and not leakage in the usual sense - it's a mathematical identity. College's `rul_seconds` label is itself defined as `run_end_timestamp - event_timestamp` (pipeline.py), using the actual known final-file timestamp, because college is a single complete run with no censoring (unlike FEMTO's test_censored/full_test split). The naive baseline predicts `mean_total_life_seconds - elapsed_seconds`, and because an expanding-window train fold always starts at the true global t=0, `mean_total_life_seconds` always equals the true total run duration exactly - making the naive formula algebraically identical to the label's own definition. It "predicts" the label because it's the same formula, not because it generalizes.
Resolution: documented, not hidden or removed. Implication for `docs/prd.md`/reporting: the college naive baseline number must never be quoted as "the model achieves 0 error" - it's a property of the within-run backtest setup, not a capability. The `extra_trees` model's college numbers (MAE ~117k-132k seconds, i.e. ~33-37h on a 128h run) are the only real college RUL evidence and should be reported as such. A more meaningful naive comparison for college would need an external reference (e.g. the FEMTO learning bearings' mean total life) rather than the run's own known end time - flagged as a possible M9 refinement, not done here (accelerated-track time-box).

## D9: naive RUL baseline's elapsed-time calculation broke the college walk-forward evaluation (2026-07-21, found running M4 against real data)
`predict_naive_baseline` computed elapsed time as `event_timestamp - group_min(event_timestamp)`, recomputed from whichever dataframe was passed to `predict()`. For FEMTO leave-one-bearing-out this happened to be correct (a held-out bearing's test set is its entire trajectory, so its own min IS its true start). For the college walk-forward, later folds' test slices start mid-run, not at t=0 - so elapsed was computed relative to the test fold's own start, not the bearing's true start, making the naive baseline think almost no time had elapsed. Real symptom: naive MAE ballooned from 108,038s (fold 1) to 342,158s (fold 3) while extra_trees stayed roughly flat (116,657 to 131,762) - the naive baseline was getting *systematically worse* in a way that had nothing to do with the model, just a broken elapsed-time reference.
Resolution: `NaiveBaseline` now stores a `bearing_start_times` dict fitted from the training data (the true earliest observed timestamp per bearing) and `predict_naive_baseline` uses that fixed reference, falling back to the predict-df's own group-min only for a bearing never seen in training (which is exactly the FEMTO LOBO case - the held-out bearing isn't in `bearing_start_times`, so the fallback correctly reproduces the old behavior there). See `artifacts/evidence/REVIEW-M4/summary.md` for before/after numbers.

## D7: PCA HI fillna(median) would fabricate temperature for zero-temp bearings (2026-07-21, found running M3 against real FEMTO data)
`fit_pca_hi`'s first version selected `bearing_temp_mean/min/max` into its top-8 features (they trend upward with degradation for the 4 bearings that have real temp files) then `.fillna(median)`-imputed them for ALL rows before scaling/PCA - including Bearing2_2 and Bearing3_2, which have **zero** temperature files (confirmed in `docs/dataset-audit.md`). That's not filling a rare gap, it's inventing an entire signal for a sensor that was never recorded for those bearings, contradicting the project's own no-fabrication rule (D6).
Resolution: `candidate_feature_columns` gained a `max_nan_fraction` filter (default 0.2 in `fit_pca_hi`), applied before feature ranking - a column that's this sparse (bearing_temp_* is ~32% NaN dataset-wide, all concentrated in whole bearings) is excluded from PCA candidacy entirely rather than imputed. Small, genuinely-sparse gaps within a selected column (e.g. FEMTO's 2/2803 acquisitions with no nearby temp match) are still median-filled - a standard, defensible practice for real sparse missingness, not the same failure mode.

## D8: PCA HI orientation sign was inverted for every bearing (2026-07-21, found running M3 against real FEMTO data)
`fit_pca_hi`'s orientation step correlated PC1 against raw pooled `sequence_index` to decide which sign makes the HI decrease with degradation. The 6 learning bearings range from 515 to 2803 acquisitions; pooling raw (non-normalized) indices lets the longest bearings dominate the correlation estimate, and the resulting sign was wrong for **all 6 bearings individually** (`trend_corr` was +0.27 to +0.73 for every bearing - HI increasing as bearings degraded, backwards).
Resolution: orientation now correlates PC1 against per-bearing life-fraction (`sequence_index / that bearing's max`, matching the normalization already used correctly in `monotonicity_trendability_scores`) instead of raw pooled `sequence_index`. After the fix, all 6 bearings show consistently negative `trend_corr` (-0.27 to -0.87). `artifacts/evidence/REVIEW-M3/summary.md` has before/after numbers.
